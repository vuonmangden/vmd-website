# PAY-002 — SePay Webhook Ingestion (Sandbox)

## Goal

Receive SePay Test Mode transaction webhooks, authenticate them with the configured API key, persist the received event before queueing it, and provide safe idempotent acknowledgement. Payment confirmation is explicitly deferred to PAY-003.

## Approved business decisions

- Endpoint: `POST /api/v1/webhooks/sepay/transactions`.
- Authentication header is exactly `Authorization: Apikey <SEPAY_API_KEY>`.
- The API key is held only in server environment configuration and compared in constant time. It must never be logged or persisted.
- This integration is for development/staging Test Mode only. It fails closed when `APP_ENV`/`NODE_ENV` is `production` until REL-001 provides a separately approved production provider configuration.
- Payload fields: `id`, `gateway`, `transactionDate`, `accountNumber`, `subAccount`, `transferType`, `transferAmount` (integer VND), `accumulated`, `code`, `content`, `referenceCode`, `description`.
- `transferType` is `in` or `out`; only valid structured payloads can enter the queue. Matching, payment confirmation, booking transition, and reconciliation are PAY-003 work.

## Scope

- Persist a sanitized raw event with unique `(provider, provider_event_id)` idempotency.
- Store payload before queueing and queue the event ID using the existing payment-webhook queue.
- Preserve a stable response for duplicates; do not process a transaction in this task.
- Document the OpenAPI endpoint and add authentication, malformed payload, and duplicate tests.

## Out of scope

- Production SePay credentials, live bank data, provider transaction processing, payment confirmation, booking updates, refunds, and reconciliation decisions.
