# PAY-003 — Idempotent Payment Processing (Sandbox)

## Scope

Process raw SePay Test Mode webhook events persisted by PAY-002. This task owns business classification, idempotent payment confirmation and reconciliation creation for synthetic room bookings only.

## Approved rules

- Auto-confirm only when `transferAmount === amountDue` and normalized `content` or `code` contains the payment intent transfer content.
- Overpayment, underpayment, incorrect/missing transfer content, or any mismatch creates a reconciliation case and never auto-confirms booking/payment.
- Processing is idempotent by stored webhook event and provider transaction identity; a repeated event cannot duplicate payment, booking transition, notification, outbox event or audit log.
- Happy path confirms payment intent and transitions a `PENDING_PAYMENT` booking to `CONFIRMED` transactionally, confirms its active resource hold/occupancy, writes audit/outbox, and enables a customer-safe status response.
- No refund is automatic. Provider details/account numbers/descriptions must not be exposed to public clients or logs.

## Excluded

- Production SePay, manual reconciliation UI, refunds, BBQ payment, and notification delivery templates.

## Verification

- Tests cover correct payment, duplicate webhook, over/under/wrong content, expired intent, mismatched booking state, transaction rollback, PII masking, authorization and stable public-safe status contract.
- Full gates, migration validation and hosted CI are required.
