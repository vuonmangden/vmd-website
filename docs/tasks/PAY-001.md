# PAY-001 — Payment Intent (Sandbox)

## Scope

Create the server-side payment-intent foundation for synthetic room bookings only. The intent uses SePay Test Mode semantics but never contains a production bank account, provider secret, or production webhook configuration.

## Approved owner decisions

- Payment expiry: room booking 24 hours; BBQ 12 hours. Values are read from `app_settings`, never hard-coded into business logic.
- Transfer content format: `VMD [TYPE][YYMMDD][RANDOM_4]`, uppercase alphanumeric, at most 25 characters, unique per intent.
- Expiry: intent becomes `EXPIRED`; the linked booking becomes `EXPIRED`; occupancy and active hold are released in the same transaction; an outbox notification event and immutable audit record are created.
- A partial payment at expiry does not cause an automatic refund; it creates a reconciliation case for an authorized admin.
- Staging uses SePay Test Mode only. Production provider credentials and real bank details are explicitly out of scope.

## Required model and API behavior

- Add forward-only Prisma migration for payment intents and reconciliation cases, with UUIDs, UTC timestamps, integer VND amounts, unique transfer content, and appropriate indexes.
- Create an internal, authenticated sandbox API for an authorized staff actor to create/read payment intents for synthetic bookings. No public payment confirmation endpoint.
- Generate deterministic-safe unique transfer content and a provider-neutral QR payload/reference; do not fabricate a bank QR image or a real payment URL.
- Idempotent creation and transactional outbox/audit writes are mandatory.
- Intent creation must reject a booking that is not `PENDING_PAYMENT`, has no active hold, has already expired, or does not belong to the sandbox lane.
- Expiry processing must be safe to retry and must not overwrite a non-pending payment state.

## Excluded

- SePay production credentials, production webhook ingestion/signature verification, real transfer confirmation, refunds, and any real bank data.
- Public checkout UI and public booking lookup UI; these follow in BKG-006/BKG-007 after this task.
- BBQ reservation implementation unless its own booking core exists.

## Tests and Definition of Done

- Unit and database integration tests for expiry settings, transfer-content uniqueness/format, idempotency, invalid booking state, transactional expiry/release, reconciliation creation, audit/outbox records, and retry safety.
- Permission, input-validation, and no-secret/no-real-bank-data tests.
- OpenAPI updated; full lint, typecheck, test, build, Prisma validation/migration deployment verification, and hosted CI pass.
